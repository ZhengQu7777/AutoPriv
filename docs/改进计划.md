# AutoPriv 改进计划

## 1. 文档目的

这份文档不是回答某一个单点 bug，而是作为当前框架下一阶段优化的总纲。

当前 AutoPriv 已经具备一条可运行的主链路：

`用户任务 -> planner -> prober -> configer -> critic -> 输出结果`

它已经能产出推荐配置，说明框架雏形是成立的；但从代码结构和运行行为来看，当前实现更接近“能跑通的原型”，还不是“职责清晰、状态明确、容易扩展”的稳定架构。

本计划的目标是：

- 保留当前项目“多模块协作”的思路
- 去掉不必要的复杂度
- 修正运行语义不清的问题
- 为后续接入真实执行器和记忆能力打基础

## 2. 对当前框架的不足

### 2.1 `planner` 职责过重，`pipeline` 职责又没有真正收口

当前 `planner.py` 里同时做两件事：

- 初始任务理解：`run()`
- 运行时逐轮调度：`decide_next()`

而 `pipeline.py` 又同时掌握：

- 状态维护
- agent 调用
- planner 更新应用
- 缺失结果兜底

当前运行结果更依赖 prompt 质量，而不是依赖可审计的代码状态机

### 2.2 planner中的decide部分重复载入 prompt

当前 `planner.decide_next()` 每次做决定的时候会重新读取prompt文件
当前对应的prompt文件内容又过于简单，没有给出例子与规定，这可能导致规划出现问题

### 2.3 `critic` 不通过后仍然得到结果，当前语义不够清楚

现在主流程里即使 `critic` 不通过，最后依然会返回：

- `config`
- `critic`
- `probe_report`
- `overall_report`
这个问题本身是合理的，但需要改得更精确：

- 问题不在于“有结果”本身
- 问题在于当前没有区分“候选结果”和“最终可执行结果”

也就是说，`critic` 不通过后不一定要立刻无条件重跑 `configer`，而是应该先由主流程判断：

- 是重新配置
- 还是重新探测
- 还是直接终止并返回一份“未通过审查的候选结果”

当前代码把这些分支语义混在一起了，所以用户才会感到结果不清楚。

### 2.4 在pipeline 中 `blackboard` 、`state` 、`observation`、`action_trace`都存在，是否需要这么多来记录当前状态与上下文

`blackboard.py` 当前只做三件事：

- 存消息
- 列消息
- 转字典

目前它的主要用途是：

- 给 prompt 提供通信轨迹
- 写到最终输出里方便查看

所以现在的 `blackboard` 更接近“事件日志”或“trace”，还算不上真正有调度意义的共享黑板。
需要考虑是否进行简化，本质上是需要维护一个上下文以及当前的状态用于决策。

## 3.框架合理设想

```text
用户任务
  -> Planner
  -> Prober（先做一次标准探测）
  -> 若探测失败/异常，则进入prober直到得到探测结果
  -> Configer（消费统一的 ProbeSummary）
  -> Critic（做审查，审查不通过需要重新进行Configer）
  -> 如果明确允许执行，再进入 Executor
```
需要思考到底是谁来控制与判断下一步

## 4.改进思路与可能的实现

### 4.1 先确定：由谁控制下一步

当前最需要定下来的原则是：

`默认主流程的控制权应该回到 pipeline，而不是继续放在 planner.decide_next() 上。`

原因很简单：

- `pipeline` 已经掌握了运行状态
- `pipeline` 负责调用各个 agent
- `pipeline` 负责兜底与最终输出
- `pipeline` 本身就是最适合承载状态机的地方

而 `planner` 更适合只负责：

- 理解用户任务
- 产出 `goals`
- 产出 `constraints`
- 产出 `probe_plan`

如果继续让 `planner.decide_next()` 决定主流程，系统就会变成：

- 代码负责执行
- prompt 负责真正的流程图

这在原型期能跑，但后续很难维护。

### 4.2 推荐的控制流改法

建议把默认流程改成“代码写死主链路，异常时再走有限分支”。

粗粒度逻辑建议改成：

```text
1. planner.run() -> 得到任务理解与探测计划
2. prober.run_startup_snapshot() -> 先执行一次标准探测
3. 如果探测失败或探测异常，则由 pipeline 判断是否重试 prober
4. configer.run() -> 生成候选配置
5. critic.run() -> 产出审查结论
6. 如果 critic 要求重配，则重新进入 configer
7. 如果 critic 要求重探测，则回到 prober
8. 如果 critic 通过，则结束配置流程
9. 只有在明确需要执行时，才进入 executor
```

这个改法的核心收益是：

- 主链路清楚
- 回退分支有限
- 谁能回退到哪一步，由代码而不是 prompt 决定

### 4.3 对 `planner` 的改动建议

`planner.py` 建议做两类收缩。

第一类：收缩职责

- 保留 `run()`
- 弱化或移除 `decide_next()`
- 如果仍然需要一个“智能路由器”，建议把它拆到新的 `router.py` 或 `decision_policy.py`

第二类：顺手优化

- 在 `__init__()` 中缓存 `planner_system.txt`、`planner_user.txt`、`planner_decide_system.txt`、`planner_decide_user.txt`
- 避免每次调用都重新从磁盘读取 prompt

粗粒度代码改动可以是：

- [planner.py](/Users/dengruotao/Desktop/code/AI_code/AutoPriv/autopriv/agents/planner.py)
  保留 `PlannerAgent.run()`
  新增 `_load_prompts()` 或在 `__init__()` 中预加载 prompt
  将 `decide_next()` 标记为过渡能力，后续迁移到新模块

如果最终决定完全收回控制权，`PlannerAction` 这个类型也可以逐步退出主链路。

### 4.4 对 `pipeline` 的改动建议

`pipeline.py` 会是这次结构调整里改动最大的文件。

推荐的方向不是继续往 `_run_core()` 里堆分支，而是把它拆成多个阶段函数。

建议新增这类函数：

- `_run_plan_phase()`
- `_run_probe_phase()`
- `_run_config_phase()`
- `_run_critic_phase()`
- `_should_reprobe()`
- `_should_reconfig()`
- `_finalize_result()`

这样主流程会从“一个大循环 + 一堆 if”变成“按阶段推进 + 少量回退判断”。

同时建议处理下面几个现有问题：

- 删除重复的 `run_with_probe_policy()`
- 不再同时维护 `state`、`observation`、`action_trace`、`blackboard` 四套上下文
- 用一个统一上下文对象替代分散状态

粗粒度代码改动可以是：

- [pipeline.py](/Users/dengruotao/Desktop/code/AI_code/AutoPriv/autopriv/orchestration/pipeline.py)
  把 `_run_core()` 拆成多个阶段函数
  删除 `run_with_probe_policy()`
  引入固定主链路和有限回退分支
  把“critic 不通过后的处理”改成显式分支，而不是只靠最终兜底

### 4.5 对 `types.py` 的改动建议

当前 `types.py` 的数据对象足够支撑原型，但不够支撑下一阶段的清晰语义。

建议增加一个统一上下文对象，例如：

```python
@dataclass(slots=True)
class RunContext:
    instruction: str
    planner: PlannerOutput | None = None
    probe_report: ProbeReport | None = None
    config_draft: ConfigOutput | None = None
    critic: CriticOutput | None = None
    executor: ExecutorOutput | None = None
    run_status: str = "running"
    retries: dict[str, int] = field(default_factory=dict)
    events: list[AgentMessage] = field(default_factory=list)
```

另外建议补充更明确的审查结果语义，例如：

- `CriticOutput` 新增 `decision`
  可取值如 `approved` / `reprobe` / `reconfig` / `reject`
- 或新增 `retry_stage`
  明确主流程下一步该回到哪一层

这样 `critic` 的输出就不再只是“批不批”，而是“为什么不批、应该回到哪一步”。

粗粒度代码改动可以是：

- [types.py](/Users/dengruotao/Desktop/code/AI_code/AutoPriv/autopriv/types.py)
  新增 `RunContext`
  调整 `CriticOutput`
  视情况弱化 `PlannerAction`

### 4.6 对 `prober` 的改动建议

`prober.py` 需要解决两个问题：

- 探测行为的语义要拆开
- 探测结果给下游的口径要统一

建议把现有方法重新整理成下面几类：

- `probe_once()`
  单次探测
- `probe_sampled()`
  在一次探测任务里做多次采样，得到稳定 summary
- `retry_probe()`
  在明确失败或异常时按策略重试

当前的 `run_startup_snapshot()` 可以保留，但建议逐步把它变成一个组合入口，而不是承载所有探测语义的总入口。

同时，建议修掉这两个细节：

- `run_once(**kwargs)` 要把参数传给 `network_probe`
- `configer` 不要再只消费 `samples[-1]`

粗粒度代码改动可以是：

- [prober.py](/Users/dengruotao/Desktop/code/AI_code/AutoPriv/autopriv/agents/prober.py)
  新增 `probe_once()`、`probe_sampled()`、`retry_probe()`
  修复 `kwargs` 传递
  补一个把 summary 转成统一输入结构的辅助函数

### 4.7 对 `configer` 的改动建议

`configer.py` 的核心职责不需要大改，但输入口径应该调整。

当前它消费的是最后一个探测样本，这会让它和 `critic` 的视角不一致。更合理的方式是让它默认消费：

- `ProbeReport.summary`
- 必要时再附原始最后一个样本作为参考

这样它的判断会更稳，也更符合“配置是根据探测结论生成”的直觉。

粗粒度代码改动可以是：

- [configer.py](/Users/dengruotao/Desktop/code/AI_code/AutoPriv/autopriv/agents/configer.py)
  把输入从 `ProbeOutput` 逐步迁移到 `ProbeReport` 或 `ProbeSummary`
  新增一个适配函数，兼容老接口，避免一次性改太多

### 4.8 对 `critic` 的改动建议

`critic.py` 最大的问题不是规则本身，而是输出语义还不够强。

当前 `CriticOutput` 只有：

- `approved`
- `risk_level`
- `issues`
- `recommendations`
- `next_agent`

但对 `pipeline` 来说，更重要的是：

- 这次是否应该回到 `prober`
- 是否应该回到 `configer`
- 是否已经彻底失败
- 是否只是“生成了参考配置，但不允许执行”

所以建议把 `critic` 从“审查文本生成器”升级成“审查决策器”。

粗粒度代码改动可以是：

- [critic.py](/Users/dengruotao/Desktop/code/AI_code/AutoPriv/autopriv/agents/critic.py)
  新增更明确的决策字段
  保留 `issues` 和 `recommendations` 作为解释
  让 `pipeline` 基于结构化字段而不是自然语言理解来回退

### 4.9 对 `blackboard` / 状态记录的改动建议

当前最合理的方向不是继续扩大 `blackboard` 的职责，而是先做减法。

建议二选一：

方案 A：把 `blackboard` 明确降级为 `RunTrace`

- 不再承担“共享黑板”这个较重的概念

方案 B：真正升级成黑板

- 支持按 `kind` 查最近消息
- 支持按阶段消费消息
- 让调度逻辑显式依赖黑板

从当前项目规模看，更推荐方案 A。

## 5. 建议的实施顺序

为了降低重构风险，建议按下面顺序推进。

### 第一阶段：先统一语义，不急着做大重构

先完成：

- 区分候选配置和最终配置
- 明确 `critic` 失败后的主流程分支
- 收回 `pipeline` 的控制权
- 删除 `run_with_probe_policy()` 这种重复接口

这一阶段完成后，系统的“行为解释力”会立刻变好。

### 第二阶段：再重构探测链路

再完成：

- 拆开采样、重试、周期探测
- 修复 `kwargs` 透传
- 统一 `configer` / `critic` 的探测输入口径

这一阶段完成后，运行时的多次探测现象就会更容易解释。

### 第三阶段：最后再做结构收口

最后处理：

- `RunContext`
- `blackboard` 的降级或升级
- `planner.decide_next()` 的迁移或删除

这样可以避免一次性重写太多文件，导致主流程失稳。

## 6. 这份计划的最终目标

这份改进计划最终想达到的，不是把项目改得“更像多 agent”，而是让它：

- 主流程清楚
- 状态语义明确
- 失败分支可解释
- 代码控制权清晰
- 后续扩展 executor 或 memory 时不需要返工主链路

如果这个目标能达成，框架就会从“能跑的原型”进入“可以继续稳定演进的基础架构”。
